# Микросервисная архитектура Feane Shop

Документ описывает выделение микросервисов из исходного монолита **FeaneMVC**, их границы, взаимодействие и используемую инфраструктуру.

## Цели декомпозиции

- Изоляция команд и масштабирование компонентов независимо друг от друга.
- Возможность применять разные жизненные циклы деплоя и настройки ресурсов.
- Минимизация связности через чётко определённые публичные API.

## Сервисы

| Сервис | Ответственность | Основные эндпоинты |
|--------|-----------------|--------------------|
| **CatalogService** | Хранит и отдаёт меню ресторана, категории блюд. | `GET /api/catalog`, `GET /api/catalog/{id}`, `GET /api/catalog/categories`, `GET /api/catalog/category/{category}` |
| **OrderingService** | Приём заказов, изменение статусов, расчёт итоговой суммы. | `GET /api/orders`, `GET /api/orders/{id}`, `POST /api/orders`, `POST /api/orders/{id}/status` |
| **ReservationService** | Управление бронированиями столиков, отмена. | `GET /api/reservations`, `GET /api/reservations/{id}`, `POST /api/reservations`, `POST /api/reservations/{id}/cancel` |
| **Gateway/BFF** | Единая точка входа для фронтенда. Оркестрирует запросы и проксирует на доменные сервисы. | `GET /api/menu`, `GET /api/menu/{category}`, `POST /api/orders`, `GET /api/orders/{id}`, `POST /api/reservations`, `GET /api/reservations/{id}` |

> ⚙️ Сервисы запускаются независимо, не разделяют базу данных и не используют общий код.

## Контракты и обмен данными

- Коммуникация осуществляется поверх HTTP в формате JSON.
- BFF выступает в роли клиента для внутренних API и обеспечивает стабильные контракты для фронтенда.
- Сервисы не вызывают друг друга напрямую — вместо этого в будущем планируется асинхронный обмен через брокер сообщений для событий (например, "Заказ создан").

### События (план)

| Событие | Источник | Назначение |
|---------|----------|------------|
| `OrderCreated` | OrderingService | Обновление аналитики, уведомление кухни |
| `ReservationConfirmed` | ReservationService | Уведомление клиента, синхронизация с календарями |

## Хранение данных

Текущая реализация использует in-memory хранилища для демонстрации границ. В production каждое доменное приложение получит собственную БД (SQL/NoSQL), что соответствует принципу "одна база на сервис".

## Развёртывание и инфраструктура

- `docker-compose.yml` поднимает 4 контейнера: 3 доменных сервиса и API Gateway.
- Каждый проект имеет собственный `Dockerfile`, что упрощает CI/CD.
- Конфигурация адресов downstream-сервисов задаётся переменными окружения `Downstream__*`.

## Миграция от монолита

1. **Выделение каталога** — перенос DTO и логики меню в отдельный API.
2. **Отделение заказов** — создание сервиса заказов со своей моделью и состоянием.
3. **Выделение резерваций** — перенос сценариев бронирования.
4. **Введение API Gateway** — фронтенд продолжает работать с единой точкой входа.
5. Эволюция: постепенный перенос оставшихся модулей (аутентификация, платежи) в отдельные bounded context.

## Дальнейшие шаги

- Добавить постоянные хранилища и миграции в каждом сервисе.
- Ввести брокер сообщений (RabbitMQ/Kafka) для асинхронных событий.
- Вынести общее в re-usable пакеты (например, контракты событий) вместо общей библиотеки.
- Настроить централизованное логирование, трейсинг (OpenTelemetry) и health-checkи.
